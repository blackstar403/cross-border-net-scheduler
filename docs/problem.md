# 问题定义

## 产品定位

电商出海网络的运维与智能调度：在卖家已有宽带、Clash/代理或 SD-WAN 之上，帮助运营发现影响经营的异常、判断可疑原因、执行受控处理或获得建议，并验证是否恢复。不卖节点或线路。

## 要验证的问题

卖家已经能联网，但后台慢、同步失败或直播卡顿发生时，是否仍难以判断问题、选择处理方法和确认恢复？这是假设，尚未通过一手访谈验证。单线路、单订阅用户也可能有此问题；多店、多出口、直播同时发生不是用户门槛。

调研先问最近一次故障、现有工具、处理过程及剩余困难。若打开 Clash 或现有工具已足够，接受反证；若指纹浏览器已解决出口绑定，不重复建设。不能断言所有服务商只提供连通，或现有产品都不提供运维。

## 能力边界

| 问题 | 可探索的处理 | 不作承诺 |
|---|---|---|
| 本地代理或配置异常 | 观测、诊断，有能力且允许时修复 | 不无依据重启或改全局网络 |
| 可控制任务争抢 | 降低非关键上传，验证并恢复策略 | 不自动拥有控制其他设备的能力 |
| 现有路径失效 | 有候选且业务允许时切换，否则建议人工处理 | 不创造备用路径或带宽 |
| 同步/平台错误 | 根据日志和接口区分可疑原因 | 不把授权、限频都归因于网络 |
| 物理距离、国际拥塞、最后一公里 | 说明限制，必要时建议联系服务商 | 不消除物理上限 |
| 店铺风控与出口稳定 | 遵守明确的业务出口约束 | 不保证不关联、不封号 |

## 成功标准

首版对一个通过调研选定的经营问题形成可复现闭环，见 [mvp.md](mvp.md)。运营知道哪个作业受影响、依据是什么、做了什么、是否恢复；没有能力时获得准确限制与下一步。网络测量、动作成功和实际经营恢复分别记录。

完整产品还需调研、编号需求、设计、测试、交付、用户反馈与商业假设的追溯，见 [PROJECT.md](PROJECT.md)。不以两个 IP 不同、节点数量或单次延迟下降证明整个产品成立。
