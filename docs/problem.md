# 问题定义

## 要解决的唯一问题

中小跨境卖家办公网是一条共享的、高峰时不够用的跨境链路。直播推流、广告素材上传、Seller Central / 广告后台、ERP 同步、多店铺登录挤在一起：

- 出口 IP 往往是同一个，平台按 IP 做关联
- 没有按应用的优先级，一场直播会被云盘和网页抢走上行
- 出了问题只能看到 ping / Mbps，看不到这场直播有没有掉码、哪个店在同步失败

现有供给卖的是连通（加速器、SD-WAN、云 GA、IPLC）。缺的是店铺级、场次级的调度和可见性。

## 痛点分层（避免把做不到的事写进方案）

### 本项目不声称能解决

| 现象 | 原因 | 处理 |
|---|---|---|
| 中美延迟下限 | 物理距离 | 选路减少绕行，不承诺变成本地网 |
| 晚高峰国际出口拥塞 | 出口容量有限 | 把更好的路径分给直播等刚需 |
| 家宽最后一公里差 | 卖家侧接入 | overlay 吃接入下限，写进限制 |
| 平台封号 / 关联 | 平台多信号判定 | 只降低「同出口串店」这一项风险 |

### 本项目要解决

1. 同办公室多店共用一个出口
2. 开播时其他流量抢上行，导致抖动 / 丢包 / 可能锁 TCP 降码
3. 故障不可见：服务商说线路正常，运营不知道后台、同步、直播哪一项坏了

## 为什么现有服务商长期不做这一层

- 卖带宽和按应用限流是冲突的
- 中小卖家客单价撑不起企业级网工交付
- 共享出口冒充独享才能做低价毛利
- 控制台面向网工（地域、监听、隧道），不面向店铺和场次

因此空档是控制面，不是又一条专线。

## 成功标准（作业，不是网络原语）

对一个 2 店、同时有一场直播的小团队：

- 两店出口 IP 不同，且演示期间不合流
- 开播后非直播上行被压低，直播侧丢包 / 抖动优于开播前
- 运营能在一块板上看到：后台打开时间、ERP 同步失败次数、本场是否降质

不把「延迟降 50%」「替代 OSDWAN」当成功标准。
