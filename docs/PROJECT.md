# 项目总图：什么叫「做完」

本仓库不是纯代码仓。钱潮杯要交的是一条能讲、能跑、能证伪的闭环：

**调研为什么值得做 → 需求锁成可验收条目 → 方案说明为什么这样做 → 代码实现选定运维闭环 → 测试证明做了 → 本机/单办公室能部署。**

后一环必须能指回前一环。没有这条链，六个文件夹填满也不算完成。

---

## 1. 两个完成线（不要混）

| | 钱潮杯完成（本阶段必须） | 产品完成（本仓库标明，不做） |
|---|---|---|
| 谁用 | 评委 + 作者能演示 | 真实中小卖家周复一周用 |
| 底盘 | 本机模拟出口 / 已有代理 | 多客户、持证线路、IP 采购 |
| 证据 | 实验室对照 + 文档引用 | 访谈样本、高峰实测、付费 |
| 上线 | 单机或单办公室可启动 | 计费、多租户、SLA、售后 |
| 不包含 | 德邻杯 BP、融资故事 | 自建 POP / 海缆 / 替代云 GA |

时间拆分见 [GOALS.md](GOALS.md)：**目标 1 钱潮杯（9 月交材料、10 月或可决赛）优先；目标 2 产品演进不阻塞交稿。** 当前只追左列。右列只允许出现在「以后不做清单」里。

---

## 2. 一个完整项目的七段（通用）

任何能交差的软件项目，本质都是这七段。缺一段，后面的东西就没有依据。

```
市场调研 → 需求分析 → 方案设计 → 代码实现 → 测试报告 → 部署上线 → 比赛/交付包装
     │          │          │          │          │          │
   为什么做    做成什么样   怎么做成    做出来     是否属实    别人能否复现
```

外加一条贯穿全程的 **边界与合规**：本项目是控制面，不是翻墙工具，不是专线运营商。

## 3. 落到本仓库：每段要有什么、做到什么算完成

### A. 市场调研 `docs/research/`

**要回答的问题：** 痛点是不是真的、现有产品卡在哪、为什么空档是调度不是专线、证据哪些能用哪些是软文。

| 产出 | 钱潮杯最低完成 | 不是 |
|---|---|---|
| 市场与客群 | 已有网络工具、仍有经营故障排查与恢复困难的卖家；单线路也在研究范围 | TAM 估算、融资级市场规模 |
| 竞品地图 | 加速器 / SD-WAN / 云 GA / IPLC / 指纹+代理，各管哪一层、短板 | 品牌排行榜 |
| 痛点分层 | 物理做不到 vs 商业不划算 vs 没人做控制面 | 把延迟/封号写成我们能彻底解决 |
| 证据台账 | 每条结论标注来源等级（官方 / 投诉 / 行业文 / 待一手验证） | 把 SEO 评测当调研 |

已有对话里的调研结论要沉淀进来，并标「待一手验证」的项，不要假装已经访谈过卖家。

### B. 需求分析 `docs/requirements/`

**要回答的问题：** 谁、在什么场景、要什么可验收结果；什么明确不做。

| 产出 | 钱潮杯最低完成 |
|---|---|
| 角色 | 运营本人（兼店长），无网工 |
| 场景 | 最近一次经营任务异常的发现、判断、处理和恢复；具体场景由调研选择 |
| 功能需求 | 每条可测：给定动作 → 可观察结果（对应 MVP 运维闭环） |
| 非功能 | 本机可跑、配置不含密钥、失败要可见、不得静默突破已声明的业务出口约束 |
| 范围 | 从 `docs/problem.md` / `docs/mvp.md` 提升为带编号的需求条目 |

需求条目编号后，设计、测试、演示脚本都引用同一编号。

### C. 方案设计 `docs/design/`

**要回答的问题：** 控制面长什么样、调度策略是什么、AI 用在哪、为什么不自建底盘。

| 产出 | 钱潮杯最低完成 |
|---|---|
| 架构 | 控制面 / 探针 / 出口适配 / 看板 四块；数据面用现成隧道或本地模拟 |
| 调度策略 | 按诊断证据和资源能力处理；保留业务约束、失败分支与恢复策略 |
| AI 位置 | 分类与策略（开播质量、是否降质、是否该让路），不接聊天大模型充数 |
| 数据 | 店铺、出口、探测样本、场次、告警；无真实店铺密钥 |
| 风险 | 物理上限、误杀上传、代理失效、合规表述 |

方案必须能一页画给评委：已有资源 → 作业观测 → 诊断依据 → 受控处理/建议 → 恢复复测；标明平台执行边界和业务约束。

### D. 代码实现 `src/` `cmd/` `web/`

**要回答的问题：** 选定运维闭环有没有可运行的最小实现。

| 模块 | 职责 |
|---|---|
| `cmd/` | CLI：检查接入、复现异常、执行受控动作、复测 |
| `src/control/` | 诊断与策略：动作条件、业务约束、执行与复测 |
| `src/egress/` | 出口适配（真实代理或本地 mock） |
| `src/probes/` | 后台时延、同步探测、直播路径质量 |
| `src/qos/` | 选定争抢场景时实现上传控制；未选时不要求该模块 |
| `web/` | 业务影响、诊断依据、处理及恢复结果，不做纯网速仪 |

实现完成 = 选定场景及失败分支能按文档在验证过的平台走通，而不是框架搭完。

### E. 测试报告 `tests/` + `docs/test/`

**要回答的问题：** 需求是否被证伪过；失败写进报告，不准只贴通过。

| 产出 | 钱潮杯最低完成 |
|---|---|
| 用例 | 每条功能需求至少一条自动或半自动用例 |
| 场景 | 正常/异常、处理前/后、不可处理或处理失败；实际作业指标与网络指标分开 |
| 报告 | 环境、步骤、期望、实际、限制（例如未接真 TikTok ingest） |
| 已知缺陷 | 列表，对应「本阶段不修」或「赛前必须修」 |

没有正常/异常和处理前/后对照不算测过调度；隔离、争抢只在选定对应场景时增加验证。

### F. 部署上线 `deploy/` + `docs/deploy/`

**要回答的问题：** 别人（或评委机器、作者比赛现场）能否按文档起起来。

| 产出 | 钱潮杯最低完成 |
|---|---|
| 本机部署 | 一条命令或短脚本：依赖、配置样例、启动看板与 CLI |
| 配置 | `.env.example`，真实密钥不进仓 |
| 运行手册 | 运维闭环、常见失败（代理不可达、无权限、无替代路径、复测无效） |
| 「上线」含义 | 单机演示环境可用；不是公网多租户 |

钱潮杯的上线 = **可复现的演示环境**，不是 App Store / SaaS 开量。

### G. 比赛交付 `docs/competition/`

**要回答的问题：** 评委 10 分钟内听懂、三问能答、材料能交。

已有 `docs/qianchao-cup.md`，完成时还要：

- 一页问题 + 方案图
- 演示脚本（与测试场景同一套）
- 与连连「跨境经营 / AI」对齐的三句话
- 禁句清单仍然有效

## 5. 追溯规则（完成检查用）

1. 每条功能需求有编号（如 `REQ-OBS-01`）。
2. 设计章节、测试用例、演示步骤引用该编号。
3. 调研里标为「物理做不到」的，需求和方案不得写成目标。
4. 代码不得实现叙事禁区（全球加速、保证不封号、通用 VPN、独立站再套 CDN）。
5. 测试报告的场景 = `docs/mvp.md` 演示脚本，不允许另写一套漂亮但没跑过的故事。

缺编号的需求，不算锁过；测了 Mbps 没测作业指标，不算测过。

---

## 6. 建议开工顺序

1. 把已有调研沉到 `docs/research/`（结论 + 证据等级），不新开调研题目。
2. 把 `problem.md` / `mvp.md` 拆成带编号的需求。
3. 一页架构 + 调度策略（设计最低完成）。
4. 按演示脚本写测试用例（先写测什么，再写代码）。
5. 实现接入检查 → 作业异常诊断 → 受控动作 → 业务复测及失败分支。
6. 本机部署脚本 + 测试报告填实测。
7. 最后收比赛一页纸。

不要从搭框架、选技术栈、做登录注册开始。
